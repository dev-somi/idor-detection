# 0006. 엔드포인트 단위, 여러 파일 코드베이스 실험 추가

- 날짜: 2026-10-24
- 상태: 채택

## 맥락
기존 실험은 단일 파일 예제 12개에서 "대상 함수"를 단위로 했다. 전체 파일이 약 1,100자라서 문맥 축소 효과가 잘 드러나지 않았다(B 501, D 569 토큰, ADR 0005). 실제 IDOR는 웹 API 엔드포인트 단위로 생기고, 인가 검사는 핸들러, 의존성 주입, 서비스 함수로 흩어져 있다. 그래서 같은 연구 질문을 엔드포인트 단위와 여러 파일 코드베이스에서 다시 실험한다. 기존 실험의 코드, 프롬프트(v1), 결과는 바꾸지 않는다.

## 결정
- **대상**: 원본 저장소(`idor-test-codebase-main`, `VAmPI-master`)는 수정하지 않고, `scripts/build_bench.py`로 `bench/`를 다시 만든다.
  - `bench/campus`: 캠퍼스 서비스(FastAPI) 원본 엔드포인트 17개(취약 6개, 정상 11개, 원본 ground_truth.md를 옮김)와 위임형 엔드포인트 8개(취약 4개, 정상 4개, `bench_src/campus_extra`)를 합쳐 25개다.
    - 원본 앱은 인가 검사가 모두 핸들러 안에 있다. 그대로 쓰면 B~D 조건의 차이가 거의 없어서 위임형 엔드포인트를 추가했다.
    - 추가한 패턴: 서비스 함수가 검사한다/검사하지 않는다, Depends 의존성이 검사한다/존재 여부만 확인한다, 검사 반환값을 무시한다, depth2 헬퍼가 검사한다/정책과 다른 기준(학과)으로 검사한다, 서비스를 거치는 공개 정보.
  - `bench/vampi_vuln`, `bench/vampi_secure`: VAmPI의 전역 스위치 `if vuln:`을 AST에서 True/False로 접어 두 빌드를 만든다.
    - 항목은 `IDOR_EXPERIMENT_PLAN.md` §3을 따른다. P1·P2는 vuln 빌드에서 양성이고 secure 빌드에서 음성 짝이다. N1~N3은 hard negative다. B1·B2는 boundary로 주 지표에서 빼고 민감도 분석에만 쓴다.
    - 빌드마다 7개씩 14개다.
- **정규화(모델 입력 코드)**: `ast.parse` → docstring 제거 → `ast.unparse`를 거친다. 그래서 주석이 모두 사라진다. 원본 캠퍼스 코드의 `# Club posts are shared content ...` 같은 정답 힌트도 함께 없어진다. VAmPI에서는 다음을 바꿨다.
  - `vuln_app` → `api_app`
  - `from app import vuln` 제거
  - `GET /` 응답 문구("VAmPI the Vulnerable API ...") → `Book API home`
  - `app.py`는 토큰 수명만 남긴 파일로 교체

  동작은 바뀌지 않으며, 실행 테스트로 확인했다.
- **정책**: 엔드포인트별로 영어 1~3문장을 직접 썼다(`bench/<이름>/endpoints.json`). 근거는 캠퍼스는 `docs/requirements.md`, VAmPI는 README와 OpenAPI description이다. VAmPI P2(비밀번호 변경)는 명세에 소유권 문구가 없어서 "본인 비밀번호만 바꿀 수 있다"는 도메인 규칙으로 적었다. 정책에는 규칙만 적고 구현 여부는 적지 않는다.
- **정답표**: `ground_truth/endpoints.json`. 판정이 "current_user가 요청자"라는 사실에 기대는 항목은 required_functions에 `get_current_user` 또는 `token_validator`를 넣었다. 그래서 정상 항목 상당수는 B(핸들러만)에서 "필요 코드 포함"이 거짓이 된다.
- **추출기**: `idor_ctx/ep_extract.py`. `extract.py`의 호출 분류와 BFS를 재사용한다. 모듈 사이 `from ... import`(상대 import, `*` 포함)와 매개변수 기본값의 `Depends(함수)`를 간선으로 본다. `Depends(require_role("admin"))`처럼 팩토리를 쓰면 팩토리 함수 전체를 넣는다. 메서드·모듈 속성 호출, 클래스, 전역 변수는 지금처럼 넣지 않고 "Calls not shown"에 적는다.
- **조건**: A_full(모델 입력 파일 전체), B_handler(데코레이터를 포함한 핸들러), C_depth1, D_depth2.
- **프롬프트 ep-v1**: SYSTEM_PROMPT와 OUTPUT_SCHEMA는 v1 그대로 쓴다. 사용자 프롬프트에 `ENDPOINT:` 줄을 더하고, 대상 함수는 `모듈.함수 (the handler of this endpoint)`로 적는다. CONTEXT NOTE 머리말은 "from the file"을 "from the codebase"로 바꾸고, 클래스에 데이터 모델과 스키마가 포함된다는 설명을 더했다.
- **생성 설정**: `GEN_OPTIONS` 그대로다(num_ctx 16384). 스모크 실행에서 A_full 입력은 캠퍼스 약 6,750 토큰, VAmPI 약 3,700 토큰이었다.
- **평가**: `evaluate.py`가 `--labels` 인자를 받고, 조건 목록은 run_meta에서 읽는다. 엔드포인트 실험은 다음 묶음별로 지표를 낸다: campus 전체 / 원본 / 추가, vampi(boundary 제외) / vampi(boundary 포함). VAmPI 짝 비교표도 낸다. 기존 함수 단위 결과로 다시 계산했을 때 metrics.csv는 완전히 같았다.
- **실행 환경**: bench 앱의 실행 테스트에는 `.venv`(fastapi 0.115.6, sqlalchemy 2.0.2, connexion 2.14.2, flask 2.2.2 등)를 쓴다. 예측, 추출, 평가는 지금처럼 표준 라이브러리만 쓴다.

## 결과
- 실행 테스트에서 모든 라벨이 실제 동작과 맞았다(campus 25개, vampi_vuln 7개, vampi_secure 7개 통과).
- 추출 커버리지(LLM과 무관):
  - 위임형 항목 중 서비스 함수와 의존성 패턴은 C에서, depth2 헬퍼 패턴은 D에서 필요한 코드가 처음 들어온다.
  - campus e16(require_role)과 e22(의존성 안의 get_current_user)는 D에서야 필요한 코드가 다 들어온다.
  - VAmPI boundary 2개는 필요한 코드가 클래스 메서드에 있어서 B~D 어디에도 들어가지 않는다.
- 한계:
  - 양성은 campus 10개, VAmPI 2개(짝)로 적다.
  - 위임형 8개와 정책 문장은 이 실험을 위해 직접 만들었다.
  - VAmPI는 모듈이 작아서 C와 D가 같다.
  - 일반화할 수 없다.
- 스모크 실행(`runs/smoke_ep_20261024-171037_qwen2.5-7b`, 3개 항목, 1회)은 흐름 확인용이고 분석에는 쓰지 않는다. 스모크 이후 미해석 Depends 항목의 표시를 `Depends(x)(...)`에서 `x(...)`로 고쳤다.
